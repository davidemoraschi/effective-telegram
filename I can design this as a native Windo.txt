I can design this as a native Windows application in C, with SQLite statically embedded and MCP communication exclusively over standard input/output.

There are three important implementation decisions to make to avoid producing something that compiles but is not genuinely MCP-compatible.

1. MCP version and compatibility
As of November 2026, the latest MCP specification is 2026-07-28, not the older 2025-11-25 revision.

This is a significant change:

The latest specification uses a stateless protocol model.

The old initialize / initialized handshake has been removed.

Protocol version and client metadata are supplied with individual requests.

server/discover provides capability discovery.

Multi Round-Trip Requests replace the previous server-initiated request model.

The stdio transport remains newline-delimited JSON-RPC 2.0.

One important distinction: stdout must contain exclusively MCP messages. Diagnostics, logging and errors go to stderr. This is mandatory for correct stdio transport behaviour.

3. One important technical constraint
There is a small conflict between your requirements:

SQLite must be embedded to produce a self-contained executable.

The official SQLite amalgamation is a generated C source file containing hundreds of thousands of lines.

The sensible solution is to treat SQLite's upstream source as a third-party vendor component, while enforcing your 500-line limit on every application-maintained source file.

SQLite officially recommends this amalgamation approach for embedding. 

SQLite
+1

If the 500-line limit must also apply to the SQLite vendor source, the requirements are incompatible with embedding the full SQLite engine in the conventional way.
